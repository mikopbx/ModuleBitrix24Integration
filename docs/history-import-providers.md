# Постановка: импорт истории звонков операторов (МТС / Beeline / Megafon) из `cdr_general`

**Статус:** РЕАЛИЗОВАНО (не задеплоено). Код в ветке develop, флаги импорта выключены — до включения ничего не отправляется. См. §9 «Что сделано».
**Дата:** 2026-09-18
**База анализа:** `serber@boffart.miko.ru`, `cdr_general` (62 470 звонков)
**Базируется на:** `bin/MtsImporter.php` + `WorkerBitrix24IntegrationHTTP::handleImportHistoricalCalls/enqueueHistoricalCall`
**Смежный отложенный план:** `docs/history-import-backfill.md` — тот же ридер `cdr_general`, но с обычными (не провайдерскими) звонками; этот дизайн — его подмножество.

## 1. Решение (финал)

**Единый импорт из общей CDR ядра `cdr_general` для всех трёх операторов**, маршрутизация по префиксу `linkedid` (`fs-mts-`, `fs-beeline-`, `fs-megapbx-`). Один тип, один ридер, один курсор. Приняты решения:

1. Источник — только `cdr_general` (не читаем `mts_cdr`/`bee_cdr`).
2. UI — 3 отдельные галки, каждая видна при установленном соответствующем модуле.
3. Старую MTS-историю глубже ретеншна ядра **не тянем** (см. §3, оговорка).

## 3. Оговорка: глубина истории MTS (принята)

`cdr_general` активно чистится (`ModuleCleanRecords` установлен), хранит ~4 мес (с 2026-05-12). `mts_cdr` — с 2025-11-17 (63 968). Внутри общего окна цифры сходятся **точно** (mts_cdr при `start≥2026-05-12` = 44 753 = столько же в ядре). То есть из `cdr_general` **не** импортируются ~19 000 старых MTS-звонков (до мая) — они есть только в `mts_cdr`. **Решено этим пренебречь** ради единого типа. Beeline/Megafon такой потери не имеют (укладываются в окно / своей таблицы нет).

Если позже понадобится глубокая MTS-история — разовый добор из `mts_cdr` тем же `enqueueHistoricalCall` (не входит в этот объём).

## 4. Архитектура

Один cron-импортёр + один action в HTTP-воркере (переиспользуем существующий).

### Источник — `cdr_general`
- Core-модель `MikoPBX\Common\Models\CallDetailRecords`, соединение `cdr.db`
  (`/storage/usbdisk1/mikopbx/astlogs/asterisk/cdr.db`, таблица `cdr_general`).
- Индексы есть на `start`, `linkedid`, `src_num`, `dst_num`, `UNIQUEID` — курсор по `start` эффективен.
- **Фильтр провайдеров** по префиксу `linkedid`. Для использования индекса — диапазонная форма вместо `LIKE`:
  `linkedid >= 'fs-megapbx-' AND linkedid < 'fs-megapbx.'` (или `GLOB 'fs-megapbx-*'`).

### Цикл прогона
1. Выборка `WHERE start >= :cursorMinusOverlap: AND start < :settledBoundary:
   AND (<включённые префиксы>) ORDER BY start LIMIT PAGE_SIZE`,
   где `settledBoundary = now − DELAY (10–15 мин)`, `cursorMinusOverlap = cursor − OVERLAP`.
2. Для каждой строки:
   - определить провайдера по префиксу `linkedid`; если его галка выключена — пропуск;
   - **фильтр внешнего номера:** хотя бы один из `src_num`/`dst_num` длиннее 6 цифр (после очистки от `+ - space`), иначе пропуск (внутренний);
   - собрать payload (та же схема, что ждёт `enqueueHistoricalCall`): `linkedid, src_num, dst_num, did, start, duration, disposition, recordingfile, from_account, crm_create, export_records_setting`.
3. Батчи по `BATCH_SIZE` → `invoke('importHistoricalCalls', ...)`.
4. Курсор `history_import_last_date` двигаем только после `IMPORT_ACK_OK`, до макс. `start` уложившихся строк; на неулёгшихся (свежее `settledBoundary`) — стоп без сдвига.

### Приёмник `enqueueHistoricalCall` (правки)
- Убрать жёсткий guard `from_account==='fs-mts'` (`:305`) → без него; направление и сотрудник резолвятся как есть (`findMtsEmployee` по `inner_numbers`/`mobile_numbers`).
- Направление для всех провайдеров определяется по тому, какая сторона — сотрудник (уже реализовано). Для Megafon `from_account` ненадёжен, но он в резолве не участвует — маршрут по префиксу уже сделан в cron.

Межисточникового конфликта нет: источник один (`cdr_general`), `mts_cdr`/`bee_cdr` не читаем. Существующие 1 560 выгруженных отсеются дедупом.

## 7a. Расширение до генерик-бэкфилла (задел на будущее)

Этот импортёр — «лёгкая половина» генерик-бэкфилла (`docs/history-import-backfill.md`): тот же ридер `cdr_general`, курсор по `start`, settled-delay, дедуп по `linkedid`. Провайдерский вариант ограничен префиксами `fs-*` и обкатывает механику на боевых данных.

Чтобы расширить на догрузку обычных звонков (модуль был выключен/упал), потребуется доработать **дедуп и сборку** — то, что провайдеры получают бесплатно из-за однострочности:

1. **Схлопывание плеч** — обычные звонки до 65 плеч на `linkedid`; собрать в один register (направление/клиент/длительность/запись). Главная новая работа.
2. **Не-бинарный дедуп.** Сейчас «есть `call_id` → скип весь звонок». Для починки сбоев нужно различать:
   - register не прошёл → строки нет → слать (работает уже сейчас);
   - register прошёл, finish упал → строка с `call_id` есть → **текущий дедуп ошибочно скипнет**, «висящий» звонок не починится → нужна семантика «дослать finish»;
   - живой поток пишет `b24_cdr_data.uniq_id = UNIQUEID плеча`, импорт — `uniq_id = linkedid`; гарантировать, что `linkedid`-дедуп срабатывает первым (иначе вторая строка).
3. **Граница «звонок завершён»** для многоплечевых — settled-delay по одному плечу мало (переводы/очереди тянут linkedid во времени).
4. **Разграничение импортёров** — генерик-ридер должен исключать провайдерские префиксы (или объединить в один ридер с общим курсором), иначе двойная обработка.

## 9. Что сделано (реализация)

Единый источник `cdr_general` через штатный `MikoPBX\Common\Providers\CDRDatabaseProvider::getCdr($filter)`
(запрос исполняет `WorkerCdr` через Beanstalk; соединение `dbCDR` напрямую не трогаем — как в `ModuleAmoCrm/bin/AmoCdrDaemon.php`). Проверено на боевой базе для всех 3 префиксов.

Нюанс `getCdr`: числовой bind (`:id:`) через воркер не срабатывает (возвращает пусто) — курсор подставляем литералом `id > <int>` (значение `(int)`, инъекция невозможна); строковый bind `:pfx:` работает штатно.

Изменения:
- **`bin/HistoryImporter.php`** (новый) — заменил `bin/MtsImporter.php` (удалён). Провайдер-агностичный cron: дескрипторы 3 операторов, курсор по `cdr_general.id`, settled-delay 900с, фильтр внешнего номера (>6 цифр), батчи по 10 через `invoke('importHistoricalCalls')`, сдвиг курсора только после `IMPORT_ACK_OK`, стоп на свежих без сдвига.
- **`bin/WorkerBitrix24IntegrationHTTP.php`** — снят guard `from_account==='fs-mts'` в `enqueueHistoricalCall`; логи «MTS import:»→«History import:»; коммент константы → HistoryImporter.
- **`Models/ModuleBitrix24Integration.php`** — +поля `import_beeline_calls`, `import_megafon_calls`, `mts_hist_cursor`, `beeline_hist_cursor`, `megafon_hist_cursor`; `mts_import_last_id` помечен deprecated.
- **`Lib/Bitrix24IntegrationConf.php`** — cron `MtsImporter.php`→`HistoryImporter.php`; новые курсоры в `$syncKeys`.
- **UI** — форма/контроллер/`index.volt`: 3 галки под `class_exists` каждого модуля (`isMts/Beeline/MegafonModuleInstalled`); save-кейсы для новых флагов и курсоров; переводы `ru`/`en`.

Проверено (безопасно, без отправки в B24):
- `php -l` всех файлов — ок.
- `CallDetailRecords::count()` из cron-контекста = 62470 — модель `cdr_general` доступна.
- Провайдерские CDR однострочные (max_legs=1) — схлопывание не нужно.
- На боевой базе `import_mts_calls=0` (все флаги off) → деплой кода ничего не импортирует до включения галки.
- Ожидаемый объём при включении: mts ~44.7к (−1235 уже выгружено), beeline ~13.6к, megafon ~1.1к.

### ВАЖНО (операционный precondition)

Cron **двигает курсор** после `employee not found`. Значит если пользователи B24 не заведены на момент импорта — такие звонки пропускаются **навсегда** (курсор ушёл). Порядок: **сначала завести пользователей B24 с `UF_PHONE_INNER` = добавочные операторов** (или `PERSONAL_MOBILE`/`WORK_PHONE` для MTS), **потом** включать галку. `NOT_READY` (холодные карты воркера сразу после рестарта) курсор НЕ двигает — это про реально незамапленных.

### Баг, найденный и исправленный при прогоне

`CDRDatabaseProvider::getCdr()` исполняется `WorkerCdr` через Beanstalk и на **таймауте под нагрузкой возвращает пустой массив** — неотличимо от «строк нет». Импортёр трактовал пустой ответ как «провайдер вычерпан» и останавливал прогон раньше времени (спасал только следующий тик cron с того же курсора — потерь нет, но неэффективно). **Фикс:** ретрай `3×(sleep 3)` на пустой `getCdr` перед выводом «вычерпан». Задеплоено, проверено (добрал остаток, затем корректно определил исчерпание).

### Правки по код-ревью (throttling + запись)

Внесены в `bin/HistoryImporter.php` после ревью:
- **#2 (запись):** гейт «ждём докачку MP3». Answered-звонок с путём к записи, но БЕЗ файла на диске и моложе `RECORD_WAIT_SECONDS` (2ч) — откладывается (стоп без сдвига курсора), чтобы `downloadRecords` успел докачать; старше порога — импорт без записи (файл вычищен). Раньше такой звонок импортировался без записи, а дедуп навсегда закрывал повторное прикрепление.
- **#3 (getCdr ≤ 1/мин):** `GETCDR_MIN_INTERVAL=60` — минимум 60с между вызовами getCdr (WorkerCdr нельзя дёргать чаще). Проверено: 3 вызова заняли 142с.
- **#4 (лимит B24 ~7 req/s на интеграцию):** `PAGE_SIZE` 500→200, `INVOKE_PAUSE=1`с между invoke-чанками, `MAX_GETCDR_PER_RUN=3` (бюджет getCdr на прогон). Импорт кормит q_req медленно, не выедает лимит, не мешает живым звонкам. Полная выгрузка идёт за много cron-тиков — осознанно.
- **#1** (курсор уходит по «employee not found») — по решению заказчика оставлено как есть (сначала заводить операторов в B24, потом импорт).

Провайдеры обслуживаются последовательно (mts → beeline → megafon): исчерпанный тратит 1 getCdr и уступает следующему в том же прогоне.

Не сделано (требует действия оператора):
- **MTS импорт** — резолвится по мобильным (`PERSONAL_MOBILE`/`WORK_PHONE`) — нужно заполнить эти поля у B24-юзеров.
- Дозагрузка пропущенных Megafon/Beeline (незаведённые операторы) — завести в B24, сбросить курсор провайдера в 0, перезапустить (дедуп по linkedid защитит уже загруженные).
- Коммит изменений в git.
