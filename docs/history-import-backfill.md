# Постановка задачи: фоновая догрузка истории звонков из `cdr_general`

**Статус:** отложено (план готов, реализация не начата)
**Дата постановки:** 2026-09-18

---

## 1. Цель и охват

Отдельный cron-импортёр, который читает общую историю звонков MikoPBX
(`cdr_general` в `cdr.db`) и догружает в Bitrix24 звонки, которых там нет —
с «опозданием» на N минут. Закрывает два случая сразу:

- звонки, потерянные живым потоком при недоступности B24 / API / протухшем токене;
- историю до установки модуля / для не-МТС инсталляций.

Опционально, **выключено по умолчанию** (галка в админке), как и MTS-импорт.

### Контекст: почему живой поток теряет звонки

- Команды register/finish живут только в in-memory `$q_req` HTTP-воркера и
  отправляются одним `sendBatch`. После отправки `$this->q_req = []`
  выполняется **безусловно** (`WorkerBitrix24IntegrationHTTP.php:1418`),
  без проверки успеха и без возврата в очередь.
- Beanstalk-job удаляется ещё до отправки в B24 (`BeanstalkClient.php:473`),
  beanstalkd в MikoPBX запущен без binlog (in-memory) — рестарт обнуляет очередь.
- Персистентного outbox в БД нет: строка в `b24_cdr_data` создаётся только
  **после** успешного register.
- Единственный самовосстанавливающийся случай — истёкший access-токен в
  пределах одного запроса (refresh + 1 повтор). Запись разговора (MP3) имеет
  настоящий retry в `UploaderB24` (8 попыток, backoff), но это только файл.

Вывод: сам звонок при сбое теряется безвозвратно. Данная задача добавляет
недостающую страховку через дозагрузку из общей истории.

## 3. Защита от дубликатов (ядро задачи)

Дубликат в B24 = два `telephony.externalcall.register` на один физический
звонок. Защита — **8 слоёв**; первые четыре уже существуют, четыре — новые.

### Существующие (проверены в коде)

1. **DB-дедуп по `linkedid`** — `FUNC_GET_EXPORTED_CALL_ID`
   (`ConnectorDb.php:1214`): `findFirst(linkedid = ? AND call_id <> '')`.
   `enqueueHistoricalCall` вызывает его перед постановкой (`:354`) и пропускает
   звонок, если он уже отправлен — живым потоком или прошлым прогоном импорта.
   Главный барьер.
2. **Идемпотентная запись** — `updateCdrByUID` (`ConnectorDb.php:1114`) вставляет
   строку только если по `uniq_id` её ещё нет. В импорте `UNIQUEID = linkedid`,
   поэтому ключ дедупа — сам звонок, а не плечо.
3. **Register-кэш 180 сек** — `telephonyExternalCallRegister` (`:1378`):
   ключ = `USER_ID + strtotime(CALL_START_DATE) + phone_index(PHONE) +
   phone_index(inner)`. Для исторического звонка `CALL_START_DATE` — реальная
   прошлая дата, ключ стабилен → повторный register в пределах прогона отбивается.
4. **`b24_cdr_data` пишется только после успешного register** — «уже отправлено»
   = «есть строка с `call_id`», и дедуп слоя 1 надёжно ловит и живые, и
   импортированные звонки.

### Новые (в этом плане)

5. **Structural: один register на `linkedid`.** `cdr_general` хранит строку на
   плечо (`UNIQUEID`). Ридер **обязан** схлопывать все плечи одного `linkedid`
   в **один** payload (см. §5.5). Структурная гарантия: сколько бы ни было
   плеч — уходит ровно один register. Без этого шага дедуп не спасёт
   (N плеч = N разных запросов до первой записи в `b24_cdr_data`).
6. **Settled-delay (задержка N минут).** Импортёр берёт только звонки, у которых
   `endtime` заполнен и `endtime < now − DELAY`. `DELAY` перекрывает завершение
   живого потока и запись строки в `b24_cdr_data`. Закрывает гонку «живой
   register прошёл, но `b24_cdr_data` ещё не записан → дедуп пуст → повторная
   отправка».
7. **Overlap re-scan + идемпотентность.** Курсор — по `calldate`
   (low-water-mark), каждый прогон пере-сканирует окно `OVERLAP` позади курсора,
   чтобы не потерять звонки на границе страниц. Повторный проход безопасен:
   слой 1 отбивает уже отправленные.
8. **Исключение `fs-mts`.** Если установлен `ModuleMtsPbx`, импортёр из
   `cdr_general` пропускает `from_account = 'fs-mts'` — эти звонки ведёт
   `MtsImporter` со своей pending-логикой записей. Не конкурируют.

**Курсор никогда не перепрыгивает «неулёгшийся» звонок:** встретив группу с
пустым `endtime` или `endtime > boundary`, прогон останавливается без сдвига
курсора за неё (паттерн `$stopAtPending` из `MtsImporter.php:239`).

### Остаточный риск

register успешно прошёл в B24, но RPC-запись `b24_cdr_data` упала / воркер умер
до неё, и это не в пределах 180 сек. Тогда следующий прогон пере-отправит →
дубликат. Вероятность низкая (локальный Beanstalk-RPC сразу после ответа).

**Опциональное усиление до нуля:** отдельная таблица / Redis-маркер
`history_attempted:<linkedid>` (TTL, ставится ДО отправки), который дедуп
трактует как «уже пытались». Минус — добавляет ~1 день и риск навсегда
пропустить звонок, чья отправка реально упала.

**Открытый вопрос к заказчику:** v1 с документированным остаточным риском
(рекомендуется) или сразу абсолютный ноль с маркер-таблицей.

## 4. Конфигурация (константы в новом cron)

```
DELAY_SECONDS   = 900    // settled-delay, «опоздание» (обсуждается: 10 или 15 мин)
OVERLAP_SECONDS = 300    // пере-скан позади курсора
PAGE_SIZE       = 200    // сырых плеч за SQL-выборку
BATCH_SIZE      = 10     // звонков на invoke (== MAX_HISTORICAL_CALLS_PER_INVOKE)
MAX_PER_RUN     = 300    // потолок звонков за прогон
MIN/MAX_PAUSE   = 2/5    // пауза между батчами
```

**Открытый вопрос к заказчику:** DELAY = 10 мин (как в исходном запросе) или
15 мин (запас против гонки; всё равно закрыто дедупом).

поля подхватятся автоматически (как было с MTS-полями).

### 5.2. syncKeys — `Lib/Bitrix24IntegrationConf.php:59`

Добавить `history_import_last_date` в `$syncKeys`, иначе апдейт курсора будет
триггерить `onAfterModuleEnable` (та же причина, что для `mts_import_last_id`).

### 5.3. UI — `App/Views/index.volt`, `App/Forms/...Form.php`, контроллер

Чекбокс `import_history_calls` (доступен всегда, не под `isMtsModuleInstalled`).
Сохранение — по образцу `import_mts_calls`. Метки `mod_b24_i_*` в
`Messages/en.php` + `ru.php`. Курсор `history_import_last_date` в UI не
показывать / не сбрасывать (аналогично MTS).

### 5.4. Обобщить `enqueueHistoricalCall` — `WorkerBitrix24IntegrationHTTP.php:305`

Единственная МТС-специфика в приёмнике — жёсткий guard
`from_account === 'fs-mts'` (`:305-308`). Заменить на проверку из белого списка
допустимых источников (`fs-mts` и `general`/пусто), либо снять guard и
полагаться на резолв сотрудника. Всё остальное (`:310-463`) —
источник-агностично.

### 5.5. Ридер `cdr_general` + схлопывание плеч (главная новая логика)

Доступ к core-модели MikoPBX `\MikoPBX\Common\Models\CallDetailRecords`
(соединение `cdr.db`). **Точные имена колонок сверить с установленной версией
ядра** — ожидаемые: `start`, `answer`, `endtime`, `src_num`, `dst_num`, `did`,
`linkedid`, `disposition`, `recordingfile`, `UNIQUEID` (+ `from_account`, если
есть).

Алгоритм прогона:

1. **Выборка страницы плеч:**
   `WHERE start >= :cursorMinusOverlap: AND endtime <> '' AND
   endtime < :settledBoundary: ORDER BY start, id LIMIT PAGE_SIZE`,
   где `settledBoundary = now − DELAY`, `cursorMinusOverlap = cursor − OVERLAP`.
2. **Группировка по `linkedid`** в PHP.
3. **Схлопывание группы в один звонок:**
   - представитель — ANSWERED-плечо (при наличии), иначе плечо с макс.
     длительностью;
   - `src_num`/`dst_num` берём с представителя → направление и `clientPhone`
     определит существующая логика `enqueueHistoricalCall` через
     `findMtsEmployee` (какая сторона — сотрудник);
   - `disposition = ANSWERED`, если ответило хоть одно плечо, иначе
     `NOANSWER`/`BUSY`;
   - `duration` — из ответившего плеча (`endtime − answer`), иначе 0;
   - `recordingfile` — из плеча, где путь непустой и файл существует;
   - `start` — минимальный по группе; `did` — с представителя.
4. **Фильтры:** пропустить внутренние (обе стороны — сотрудники — уже отсекается
   в enqueue), сервисные без внешнего номера, `from_account='fs-mts'` при
   наличии ModuleMtsPbx.
5. **Формирование payload** ровно один на `linkedid` (та же схема, что ждёт
   `enqueueHistoricalCall`): `linkedid, src_num, dst_num, did, start, duration,
   disposition, recordingfile, from_account, crm_create, export_records_setting`.

### 5.6. cron `bin/HistoryImporter.php`

Скелет — копия `MtsImporter.php` с заменой источника:

- lock-файл `history_importer.lock`;
- guard `isEnabled`, `is_object($settings)`, `!empty($settings->portal)`,
  `import_history_calls === '1'`;
- курсор `history_import_last_date`;
- цикл выборки (§5.5) → батчи по `BATCH_SIZE` → `invoke('importHistoricalCalls',
  ...)` (тот же action!);
- сдвиг курсора **только** после `IMPORT_ACK_OK` до макс. `start` уложившихся
  групп; на первой неулёгшейся группе — стоп без сдвига;
- обработка `IMPORT_ACK_NOT_READY` (холодный воркер) — курсор не двигать.

### 5.7. Регистрация cron — `Lib/Bitrix24IntegrationConf.php:253`

Рядом с MTS:

## 6. Матрица краевых случаев

| Ситуация | Поведение | Слой защиты |
|---|---|---|
| Звонок уже ушёл живым потоком | Пропуск | 1 (DB-дедуп) |
| N плеч одного звонка | 1 register | 5 (схлопывание) |
| Гонка с живым register | Не берём < DELAY | 6 (settled-delay) |
| Звонок на границе страницы | Ловится overlap, дубль отбит | 7 + 1 |
| Внутренний звонок | Пропуск | enqueue `:318` |
| Нет сотрудника по номеру | Пропуск (лог) | enqueue `:334` |
| Повторный прогон импорта | Пропуск отправленных | 1 |
| МТС-звонок при обоих импортах | Ведёт только MtsImporter | 8 (fs-mts excl.) |
| Незавершённый звонок (`endtime` пуст) | Не берём, курсор стоит | 6 |
| register ok, но `b24_cdr_data` не записан >180с | Возможен дубль (редко) | остаточный риск §3 |

## 7. Тестирование

- Юнит: схлопывание плеч на реальных дампах `cdr_general` (вход/исход/очередь/
  перевод/пропущенный/интерком).
- Дедуп: прогнать импорт дважды подряд → второй прогон 0 отправок
  (лог `already sent`).
- Гонка: живой звонок + запуск импортёра сразу → импортёр не берёт
  (settled-delay), после DELAY — дедуп ловит.
- Курсор: неулёгшийся звонок в хвосте страницы не двигает курсор.
- Совместимость с МТС: обе галки вкл → нет двойной отправки fs-mts.
- Верификация на боевом `boffart.miko.ru` (деплой scp + kill воркеров).
